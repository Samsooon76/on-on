# Limitations connues

- Les appels et SMS réels restent désactivés jusqu'à la rotation des identifiants Twilio exposés dans l'ancien document de plan et à la configuration d'identifiants neufs dans l'environnement serveur.
- Les comptes de test et les utilisateurs Supabase doivent être invités/créés par un administrateur; aucune inscription publique n'est prévue.
- La présence Realtime n'éveille pas une application mobile. La réception mobile dépend de PushKit/CallKit et FCM correctement configurés et validés sur appareils réels.
- L'application web/API et le schéma sont le premier jalon. L'application Expo existe et ses bundles passent, mais iOS/Android ne sont pas déclarés supportés avant builds signés et essais d'appels sur appareils réels.
- Le worker serveur réconcilie les appels voix dont un callback a été manqué et les SMS dont le `MessageSid` est connu. Un SMS incertain sans SID est signalé pour contrôle manuel; aucun renvoi automatique n'est fait. Le worker exige des credentials Twilio autorisant la lecture des ressources Message.
- Le plafond quotidien compte les SMS persistés avant la requête fournisseur, même si Twilio refuse leur création; aucun remboursement du compteur n'est prévu pour ces tentatives.
- L'encodage et le nombre de segments SMS affichés sont une estimation locale des limites GSM-7/UCS-2; ils ne garantissent ni le traitement final du fournisseur ni un tarif. La configuration d'encodage du compte et le canal peuvent modifier le résultat.
- L'environnement de démonstration, les credentials push et le déploiement Railway nécessitent l'accès au dépôt `Samsooon76/on-on` et une configuration distante distincte; GitHub est inaccessible depuis l'environnement actuel et aucun projet Railway Onoff n'a été créé.
- La machine de développement n'a pas Xcode complet, simulateur iOS ni SDK Android/ADB; sa version Java 8 est également trop ancienne pour la chaîne React Native actuelle. La compilation native doit être faite sur un runner macOS/Xcode et un environnement Android avec JDK compatible.
- La connexion Realtime invalide les listes et l'interface recharge l'état; aucun cache métier hors ligne persistant n'est livré.
- L'autorisation des topics Realtime privés est calculée à la souscription et mise en cache pour la connexion. Le client rejoint les topics avec le JWT renouvelé; les routes API refont les contrôles de droits à chaque requête et les événements Realtime ne contiennent pas de numéro ni de texte. Un droit retiré peut donc laisser passer des invalidations jusqu'au renouvellement/rejoin ou à l'expiration du JWT; la durée Auth exacte doit être fixée et vérifiée avant déploiement.
- La réservation d'un onglet voix utilise Web Locks, disponible seulement en contexte sécurisé et entre onglets de la même origine. Un navigateur sans cette API affiche la voix comme indisponible; cette reprise reste à valider dans la matrice navigateur retenue.
- Le Web distingue chargement, absence de résultats, erreur API et perte réseau; la permission microphone est demandée au lancement d'un appel. Focus clavier, libellés d'actions et contrastes principaux ont été améliorés, mais aucun essai de lecteur d'écran ou de navigation clavier sur navigateur réel n'a été réalisé.
- Aucun compte ou ligne n'existe actuellement dans le projet hébergé; un administrateur doit les configurer avant d'utiliser l'interface.
- Les données métier ne sont pas purgées automatiquement. Une période de rétention et une procédure de suppression doivent être définies avant d'utiliser le système avec de vraies données personnelles.
