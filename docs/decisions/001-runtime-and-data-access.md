# Décision 001 — Runtime et accès aux données

- Date : 2026-09-25
- Statut : accepté pour le prototype
- Runtime : Node.js 24.21.0 LTS et pnpm 11.9.0; les dépendances directes sont épinglées et le lockfile versionné.
- API : Fastify dans un monolithe modulaire TypeScript.
- Accès SQL : les requêtes API portent le JWT utilisateur afin que RLS s'applique; le navigateur ne fait pas d'écritures métier directes. La clé privilégiée sert uniquement aux opérations de provisionnement et callbacks Twilio qui n'ont pas de session utilisateur.
- Isolation : toutes les ressources métier sont liées à une organisation; appels et messages exigent aussi une affectation explicite de ligne.
- Environnements : les migrations, l'introspection et les types ciblent le projet Supabase hébergé `onoffv2` (`mzqycbxnbyxeivdduhrl`). Les scripts du dépôt ne démarrent, ne réinitialisent et ne testent aucune instance Supabase locale.
- Opérations atomiques : les fonctions `SECURITY DEFINER` authentifiées (`issue_call_intent`, `prepare_outbound_message`, `set_device_voice_state`) sont appelables avec le JWT utilisateur uniquement. Elles revérifient l'utilisateur, l'appartenance, l'affectation de ligne, les paramètres, l'idempotence, le quota ou l'identité de l'appareil. Les callbacks restent `service_role` seulement. `search_path` est vide et les références SQL qualifiées.
- Alertes : l'advisor Supabase signale quatre fonctions `SECURITY DEFINER` exécutables par des utilisateurs authentifiés (`issue_call_intent`, `prepare_outbound_message`, `list_pending_outbound_messages` et `set_device_voice_state`). Leur portée est volontaire et étroite; chaque fonction vérifie `auth.uid()`, l'appartenance et l'affectation active avant d'agir ou ne retourne que les opérations incertaines de cet utilisateur. Les grants restent limités à `authenticated`, et aucun client ne reçoit la clé secrète Supabase. Pour les appareils, l'UPDATE RLS direct reste réservé à la révocation; le RPC ne peut modifier que la présence de l'appareil propre, actif et rattaché à une appartenance active.
- Présence voix : le navigateur actualise `devices.voice_registered_at` toutes les 30 secondes. La fonction `begin_inbound_call` ne route que vers les appareils dont la présence date de moins de 90 secondes; une fermeture ou suspension d'onglet cesse ainsi de les rendre joignables après expiration.
- Présence mobile : l'inscription push native est ciblable pendant l'arrière-plan et l'application fermée, tant qu'elle n'est pas explicitement révoquée. L'application renouvelle son Access Token avant expiration lorsqu'elle reste ouverte et nettoie l'inscription au changement de compte ou à la révocation locale.
- Aperçus SMS : `latest_conversation_messages` est `SECURITY INVOKER`, restreint la requête à la ligne et aux conversations fournies, et laisse les politiques RLS filtrer les messages. Il retourne au plus un message par conversation sans hypothèse sur le volume de messages.
- Synchronisation : les topics Realtime sont privés et ciblés par organisation, ligne/capacité ou utilisateur. Les triggers publient seulement identifiant, type, statut/version et date; le client relit le contenu avec l'API après chaque invalidation. Le changement d'utilisateur ferme ses anciens topics.
- Raisons : commencer petit, faire de Postgres/RLS un contrôle supplémentaire, et éviter de mettre une clé privilégiée dans un client public.
